Work the prompt plan.

Two modes. Plain `/adw:next` is attended: it works the current chunk's steps in order and stops at the chunk boundary for review. `/adw:next auto [N]` is unattended and hold-only: it works up to N steps (default 3) in a worktree, opens a PR, and never merges.

Both modes drive `prompt_plan.md` through two stdlib scripts. Call them; do not hand-edit the plan file and do not compose the git commands yourself.

```bash
PLAN="${CLAUDE_PLUGIN_ROOT}/scripts/next_plan.py"     # grammar: validate, migrate, status, next, batch, brief, set, append
AUTO="${CLAUDE_PLUGIN_ROOT}/scripts/next_auto.py"     # runs: preflight, start, step-begin, gate, commit, set, append, size, review-package, verdict, record-commit, revert, wrap-up; run-less: check, pr-opened, plan-approved
```

A plan whose Conventions carry `Record` (the delivery-record appender's command followed by the record's slug) has a delivery record at `docs/records/<slug>.md`. The scripts append to it at their own call points and commit it; the loop never edits it by hand. They run the appender as committed on origin's default branch, from a scratch worktree, never the tree's own copy that a step could have rewritten; for an attended session that branch is origin/HEAD, which `git remote set-head origin -a` sets. A Record command that names no file the tree tracks has no committed copy to run and is apparatus.

The plugin's Stop hook holds an attended turn to the plan's Test: while the plan has an open step and the tree has changes beyond the plan and the record, a turn ends only on a green Test run; a red one blocks with its tail, node's TAP `not ok` lines followed by the last 40 lines, and after three blocks on one failure the fourth stop is allowed and, with `Record`, recorded as `gate.overridden`, and a check record that matched the record before that append takes the new hash and snapshot, so the step's next `check N` accepts the line. It reads each check record against the step it names. A record at two failures, or whose step is `BLOCKED` or `FAILED`, is the loop's own stop and stands it down. A record whose step is `DONE` and whose base is no longer HEAD, left by a commit made by hand, and one whose step is `PENDING` or no longer in the plan, is stale and gates nothing, whatever its failure count; a `DONE` record whose `check N` passed at the current HEAD stays live, since a commit made part way through the step also moves HEAD off its base. Any other record lives from `check begin N` to `commit N` and gates the stop whatever state the next step has, so a committed step in its boundary fix round is gated too. With no live record, it gates only when the plan's first step not yet done is `IN PROGRESS`: it stands down at a step that is not `IN PROGRESS` in that place, one not yet begun, `BLOCKED` or `FAILED`, and at a finished plan, and a later `BLOCKED` step does not stand it down. It stands down during a run started from this checkout and in a run's own worktree, and on a plan with no Test; a run live from another worktree stands nothing down. It judges the session's own tree alone and reads no other work tree: a tree with no plan, or with no live check record and no `IN PROGRESS` step, stands it down, so another pane's Test never runs from this stop. A stop whose tree hashes as `check N` hashes it to the live record's `passed_tree` is allowed with no Test run, since a green check vouched for that tree, the plan aside; the Test runs only when the tree moved since that check, and a live record with no `passed_tree` runs it as before, one from an engine before 3.5.8 or from a check that has not passed. A Test still running after 540 s is killed and the turn ends with exit 1. A block prints one line on stdout; an error the hook cannot read past exits 1, which shows, and never blocks. A fix round abandoned before any change leaves a live record: remove `.next-auto/attended/step-N.json` by hand.

A plan whose Conventions carry `Test-files` (comma-separated glob patterns, such as `**/*.test.mjs, **/*_test.go`) has prove-red in `check N` and `gate K` take a staged file as a test when it matches one of them, in place of the built-in rule that knows Python test files only; a acme/platform plan copies `projects.yml`'s `ai_dlc.test_patterns` into it.

A plan whose Conventions carry `Toolchain-files` (comma-separated glob patterns, such as `CLAUDE.md, .claude/**`) names the `CLAUDE.md` and `.claude/` paths it commits on purpose. Attended `check N` and `commit N` admit exactly the staged paths one of them matches as a whole path, where they would otherwise refuse with `staged toolchain file`; every other staged-safe rule (the secret-shaped name, the run directory, the 1 MB cap, the secret-shaped content) still applies to them, and `check_gate_config` still wants a `CLAUDE.md` named in the brief. Auto mode ignores the line, and `gate K` refuses those paths as before.

## Before either mode: validate the plan

```bash
python3 $PLAN validate prompt_plan.md
```

Exit 0 and you proceed. Exit 2 prints line-numbered reasons.

In interactive mode, show the owner the reasons and offer to migrate: `python3 $PLAN migrate prompt_plan.md` rewrites a legacy plan into the grammar and leaves a `.bak` beside it. **Migrate only on his explicit yes**, then re-validate and show what changed. The migrated Conventions carry `- Run: uv run python -m PACKAGE`; validate exits 2 on that placeholder until the owner names the package, so ask for the name and fill it before re-validating. In auto mode, an invalid plan is a refusal; print the reasons and stop.

## `/adw:next` attended

The attended loop works a batch: the steps from the first unfinished step through the last step of its `## Chunk`, or through the last step of the plan when the plan has no chunks. It stops at that boundary for review, and earlier only on the closed stop list below. Every step in the batch runs the full per-step procedure; nothing is shortened because the step is inside a batch.

**Before the first step.**

1. **Clean-tree check.** `git status --porcelain` must be empty, apart from `docs/records/<slug>.md` when the plan carries `Record`: a pending record line is the scripts' own, not dirt. If it is not, stop and show the owner what is uncommitted. When the plan's first open step is `IN PROGRESS`, or a step is `DONE` and its check record `.next-auto/attended/step-N.json` has its `base_head` or its `passed_head` at HEAD, whatever state the steps after it have, the changes are that step's earlier work and the stop is stop (c): record it with `python3 $PLAN set prompt_plan.md N blocked-decision --note-file /tmp/note.txt`, the note reading `Decision: resume or revert step N's earlier work`, and append the same note to Decisions, so the Stop hook stands down there. The owner decides which, as at a stop on red. A `DONE` step at HEAD is a fix round an earlier session left when HEAD's subject begins `feat(step-N):`, and otherwise a step whose `commit N` refused or failed. A check record at two failures makes the stop stop (a), not stop (c), marked as on red with `python3 $PLAN set prompt_plan.md N failed --note-file /tmp/note.txt`, since `check N` would refuse at once; a resume of it records the batch base as item 2 does and begins the step again at item 4 on a clean tree, since `check begin N` refuses the earlier work and resets the count. Every resume begins with `python3 $PLAN set prompt_plan.md N in-progress`, so the Stop hook gates the resumed work. On a resume of a step that was `IN PROGRESS` below two failures, record the batch base as item 2 does, then continue step N in the same session at per-step item 5 when its check record exists, or at item 4 when it has none. On a resume of a fix round, record the batch base, which is step N's commit, and continue the boundary's fix round at its fix: the failing test first, the Test and Lint commands, `python3 $AUTO check N`, `set N done` and `commit N`, with no second `check begin N`, since its record exists, then its re-review, `review-package N --base <sha>` from that base and `verdict N --round 2`, and `record-commit` with `Record`. On a resume of a commit that did not land, record the batch base as item 2 does, then run `check N` again if the tree moved since it passed, then `set N done` with its evidence and `commit N`, and go on at per-step item 14. A new `/adw:next` on the same dirty tree stops here again. Never start a batch on top of unrelated changes.
2. **Record the batch base.** `git rev-parse HEAD`, kept for the review package at the boundary.
3. **Announce the batch.** Ask the plan tool which steps run and where the batch stops, then print its second line verbatim as the announcement, so the numbers are computed, not judged:
   ```bash
   python3 $PLAN batch prompt_plan.md
   ```
   The first line is JSON (`steps`, `first`, `last`, `boundary`, `chunk`). The second line is the sentence: `Running Steps 5 to 8, stopping at the end of Chunk B (the reviewer runs there).` for a chunked plan, `stopping at the end of the plan` for an unchunked one. An empty `steps` list means nothing is pending; say so and stop.
   When the latest prompt stamp carries a context percentage, pass it as `--context-pct N` on that call and the sentence adds `or at 60 percent context`; the percentage is the remember plugin's, printed only while `${TMPDIR}/claude-ctx-pct` holds a value. When the stamp carries no percentage, print one further line after the announcement: `No context percentage in the stamp; the chunk cap alone applies.`

**Per step**, in batch order:

1. **Pick the step.** `python3 $PLAN next prompt_plan.md` gives the first step that is not finished, with its chunk and whether it is the last of that chunk. If it looks already done, say so and ask rather than guessing; on the owner's confirmation mark it done and move on.
2. **Clean-tree check.** `git status --porcelain` must be empty before each step starts, apart from `docs/records/<slug>.md` when the plan carries `Record` (the previous step's `step.done` line waits there for this step's commit). A dirty tree here is stop (d): show him what is uncommitted and stop.
3. **Mark it started.** `python3 $PLAN set prompt_plan.md N in-progress`.
4. **Record the base.** `python3 $AUTO check begin N` records base HEAD, the baseline test counts, and the step's brief under `.next-auto/attended/`, and arms nothing. It refuses a tree dirty beyond the plan file and, with `Record`, the delivery record. It removes every earlier `check-N.log`. With a `Shares` line in Conventions it refuses, exit 1 with one line naming the tree and the class, when another work tree of the repository has a live plan that shares a class with this one, live meaning a step `IN PROGRESS`, a check record under `.next-auto/attended/` or a run marker under `.next-auto/`: `docs` never counts, and a plan with no `Shares` line, a finished plan and a listed tree whose directory is gone count for nothing. On that refusal a step item 3 marked started goes back with `python3 $PLAN set prompt_plan.md N pending` and the loop stops, naming the other tree: an `IN PROGRESS` step counts as live, so a step left started would refuse that tree's next begin in turn. A fix round's `DONE` step stays `DONE`: the refused begin wrote no record, so the step blocks nobody, and a `PENDING` step would stand the Stop hook down for the whole fix. With `Record` in Conventions it first asks the delivery record whether this plan's hash is approved: a `CHECK FAIL` naming the missing `plan.approved` line prints the hash, and no step runs until the owner approves that plan on the record. The loop never appends `plan.approved` itself: the approval is `python3 $AUTO plan-approved --by <login>`, run only on the owner's word with his login, which appends `plan.approved` for the plan's hash through the default branch's appender and prints the hash, and the line rides in the next commit that touches the record. Never re-issue it inside a retry round: the record carries the failure count, and a fresh record would reset it. The boundary's fix round is the one place it runs again, for a step already committed.
5. **Write the failing test first.** Run the Conventions' Test command and **paste the failing output**. Say in one line why that failure is the expected one.
6. **Implement** the smallest change that makes it pass. Nothing the step did not ask for.
7. **Green.** Run the Test command again and **paste the passing output**.
8. **Mutation check**, unless the step's `Mutation:` line says `n/a`. Break the guard the new test asserts on one way, run the test, require red; restore, break it the other way, run, require red again; restore and re-run to green. Paste the evidence. A test that survives both mutations is not testing anything, and the step is not done.
9. **Eval**, if the step is `Eval: yes`. Run the Conventions' Eval command and read the exit code per `Eval-codes`. Under `apparatus`, 0 is pass, 1 is fail, 2 and 3 mean the apparatus is broken. An apparatus code is a `BLOCKED (apparatus: ...)`, not a failed step: mark the step `blocked-apparatus` as the apparatus stop below says, and stop without touching the system under test.
10. **Lint.** Run the Conventions' Lint command clean.
11. **Check.** `python3 $AUTO check N` stages the tree and runs the gate's checks run-less: staged-safe, gate-config against the brief, prove-red against the recorded base, Test, the collected, skip, and xfail counts against the baseline, and then Lint. Prove-red runs in a scratch worktree at the base, the step's tests written into it and then every `node_modules` the tree has beside a directory the scratch holds linked at its own path, nested installs such as `infra/node_modules` and a new package's own install included; when every failure there is a module that does not resolve (pytest's `ModuleNotFoundError`, node's `ERR_MODULE_NOT_FOUND` or a `require` with its stack, Bun's `Cannot find module` or `Cannot find package`) and one of them is not the step's (a file the step adds or changes: a dotted Python name at the top level, under `src/`, or under a root the tree's `pyproject.toml` declares in `[tool.pytest.ini_options].pythonpath`, a relative or absolute JavaScript path, a package never; or a relative or absolute JavaScript path the step's tree holds nowhere, since the tree no longer needs it or Test fails there), the red proves nothing and the check is `CHECK APPARATUS`, which counts no attempt unless the step also failed another check, Test and the counts included. Only failed tests and the errors a file fails to load with are read, so a resolution message a passing test logs counts nothing; a failing todo never fails the run and is not read, a test cancelled by its parent counts only through the parent's failed hook, and a timed-out test is a failure of another kind. A name the step adds to an existing module stays red, as does any run from a runner whose summary the engine does not read. Known limits: a tsconfig `paths` alias reads as a package, and a workspace package the step adds or changes resolves through the tree's install, so its base run can pass. A fix round, `check begin N` on a `DONE` step, whose every staged path is documentation (`.md`, `.rst`, `.txt`) or changes only comment lines by its language's markers, no unchanged line moving into or out of a `/* */` block, skips prove-red and writes `red: n/a` with `red_reason: comment-only fix round`; Test, the counts and Lint still run. A step whose tests pass at the base is proved red by the step's `Guard-mutation:` line: prove-red applies its replacement in the scratch and runs Test again, and a red run proves the guard. It reads the step's changes against the recorded base, not HEAD, so a commit made part way through the step, such as a red test committed on its own, stays in the check; a HEAD that no longer descends from that base, after a reset or a rebase that rewrote the base, is `CHECK APPARATUS`; a pull during the step, merge, rebase or fast-forward, is not caught while the base is already upstream, so pull only between steps. Lint is judged as the gate judges it: a non-zero exit is `Lint failed: <last line>`, a red attempt like a failing Test, and a Lint that cannot start is `CHECK APPARATUS` with `Lint unavailable: <text>`, which counts no attempt unless the step also failed another check. Exit 0 is `CHECK PASS`, and it writes `.next-auto/attended/result-N.json`, the step's evidence for the delivery record (base head, passed and collected counts, prove-red, lint); any other outcome removes that file. A pass also records `passed_tree` on the step's check record, the hash of the tree it checked with the plan left out, which the Stop hook compares at a stop. Each check writes the Test command's output, pass or fail, to `.next-auto/attended/check-N.log`, so a failed check is one file read; a check whose Test does not run leaves none, and `commit N` and the next `check begin` remove it. The counts read pytest's summary, or the node test runner's and Bun's, summed when one Test runs both; any other runner records zeros. With `Record` in Conventions the check also refuses a delivery record that changed since `check begin N`: only the engine's own appends write it, `commit N`'s after the commit and the Stop hook's `gate.overridden`, whose line the check record takes. Exit 1 prints one `CHECK FAIL` line per reason in the gate's wording and counts as a red attempt; fix the cause and run `check N` again, never `check begin N`. Exit 2 is `CHECK APPARATUS`, a `BLOCKED (apparatus: ...)` stop. The check leaves the working tree and the index as it found them. Under the Test-repo exemption (a step whose header carries `Test-repo:` and `Test:`, its tests living in another repository), `check N` runs that command as the step's test evidence in place of prove-red and the counts, admits only the plan, the record and `docs/` in the index, writes `red` as `external` with the command's exit and last line, and refuses with `external Test failed: <last line>` (a red attempt), `external Test unavailable: <text>` or `external Test still running after 540 s` (both `CHECK APPARATUS`); its `check-N.log` carries the external command and its exit code on its first line, then the local output.
12. **Mark it done** with evidence, not assertion:
    ```bash
    printf 'mutation killed both ways, CHECK PASS' > /tmp/note.txt
    python3 $AUTO set N done --note-file /tmp/note.txt
    ```
    The plan change rides in the step's commit below, so the note cites the test, mutation, and check evidence; `set N done` reads the step's result file and appends its evidence clause after `; ` (`check: <passed> passed of <collected> collected at base <head8>, lint <lint>, red <red>`, with `external Test exit 0: <last line>` under the exemption), so the suite numbers are never typed, and a second set with the same note changes nothing; `next_plan.py set` refuses `done` and points here. It refuses, exit 1 and the plan unwritten, a note whose own numbers disagree with the record (`SET REFUSED step N: the note says 12 passed, the check record says 2176`, over the forms `<n> passed`, `suite <n>`, `<n> tests green` and `<n> green`, and a `CHECK PASS at base <sha>` that is no prefix of the record's head; a count with another unit, mutants or commits or another repository's PASS lines, is not judged, and the clause the engine appended is never judged, so a second set with the note as the plan carries it still changes nothing), a note whose mutation claim disagrees with the step's `Mutation:` header (`mutation killed` on an n/a step, or missing on a required one; change the header line, not the words), a result file a commit already used (`the result file was used by commit <sha8>; run check N again`), and a step with no result file unless the note says `no check N: <why>` in one sentence (`SET REFUSED step N: no result file; run check N, or write "no check N: <why>" in the note`); a result file that does not parse is `SET APPARATUS step N: result file unreadable: <why>`, exit 2. A focused run's count, the red and green of the step's own tests and the mutation control, is written in none of the four forms (`18 of the step's tests pass`, `control 18 pass`): the scan cannot tell a focused count from a suite count, and a note reworded to dodge it has lost the check. A fix round's note carries the fix's evidence only, since the first round's count and base are not this record's; the first round's evidence stays in the commit history. The commit sha is the line the next item prints. Write the words `mutation killed` when the mutation check ran: `commit N` reads the note for the delivery record's `mutation` value (`reported`; `n/a` comes from the step's `Mutation:` line, and anything else is `missing`).
13. **Commit on green.** One operation, alone in its Bash call:
    ```bash
    python3 $AUTO commit N
    ```
    With no run live it stages the tree, commits at the root as `feat(step-N): <step title>` (`--title` overrides), removes the step's check record and brief, prints `COMMIT <sha>`, and writes no run state. Pre-commit hooks must pass; never `--no-verify`. A formatter that modifies files is re-added and retried once by the script. Nothing is chained to this call: no test run, no fetch, no pipe. With `Record` in Conventions it refuses (`COMMIT REFUSED`) without the step's result file, adds the commit sha and the mutation value to that file, and appends `step.done` through the Record command; the line stays uncommitted and rides in the next step's commit or the boundary's record commit. It also refuses a result file a commit already used, and a tree that differs from the one the check passed, the plan and the record aside (`the tree changed since check N passed; run check N again`). `COMMIT <sha> RECORD FAILED` (exit 2) means the commit landed and its line did not: stop and report it, and never re-run `commit N`. `COMMIT APPARATUS` (exit 2) means git could not run: it is stop (b), and the step is marked `blocked-apparatus`.
14. **Next step.** A completing step is not a stop. When the step was the last of the batch, go to the boundary below; otherwise begin the next step at item 1.

**Stops.** The batch rule: the loop works every step of the batch and stops at the end of the chunk, or the plan, for review. Inside a batch it stops early only on:

- (a) red after the second attempt at a step; a failed `check` counts as a red attempt.
- (b) `BLOCKED`, apparatus or decision, including an eval apparatus exit code and a `CHECK APPARATUS` or `COMMIT APPARATUS` line. An apparatus stop is recorded with `python3 $PLAN set prompt_plan.md N blocked-apparatus --note-file /tmp/note.txt`, the note naming the command and its exit, so the Stop hook stands down there as it does at the stop on red.
- (c) a genuine decision under the ruling-versus-decision rule below, recorded with `python3 $PLAN set prompt_plan.md N blocked-decision --note-file /tmp/note.txt` and the same note, starting with `Decision:`, appended to Decisions.
- (d) a dirty tree at step start.
- (e) a Critical reviewer finding that survives one fix round at the boundary.
- (f) context: at each step boundary the loop reads the latest stamp and stops at that boundary with reason `context at N percent` when N is 60 or more. The percentage comes from the remember plugin's stamp and is absent until the statusline writes `${TMPDIR}/claude-ctx-pct` on that machine; with no percentage the chunk cap alone applies.

Rulings, Important and Minor findings, and a step completing are never stops; they are recorded and the batch continues. The loop may always stop earlier than the boundary. It never runs past one: a step under the next `## Chunk` header begins only with a new `/adw:next` or the owner's word.

**On red.** Stop and show the state: the failing output, what you changed, what you think is wrong. Do not revert, do not keep trying past the second attempt, and do not weaken the test. Mark the step with `python3 $PLAN set prompt_plan.md N failed --note-file /tmp/note.txt`, the note saying what failed, so the Stop hook stands down at this stop. The owner decides what happens next; resuming the step is `python3 $PLAN set prompt_plan.md N in-progress`.

**Rulings versus decisions.** You will hit ambiguity, and most of it you resolve yourself and record. An ambiguity the spec, the plan, or the surrounding code settles is a ruling: record it and keep going. The cost clause is the point; it tells the owner which rulings to check.

```bash
printf 'Ruling: <what you decided> / <why the spec or the code settles it> / <what it costs if this is wrong>' > /tmp/note.txt
python3 $PLAN append prompt_plan.md decisions --note-file /tmp/note.txt
```

A question is genuinely the owner's only when it is a design fork the spec does not answer and the two branches lead to materially different work, a keep-or-delete question about existing behavior or data, or anything touching credentials, security posture, or data loss. That is stop (c): the append above, `set N blocked-decision`, and you stop. Do not use it to avoid a judgment call the spec already covers, and do not use it as a way to stop when the work is merely hard.

**At the chunk boundary.** When the last step of the batch is done, render the review package from the batch base recorded before the first step:

```bash
python3 $AUTO review-package N --base <sha>
```

It writes `review-<N>.md` run-less. Dispatch the `adw:next-reviewer` agent against it with fresh context, passing the package path. Record every round, the first review and any re-review, `Approved` or not: save the reviewer's report verbatim with the Write tool (never a Bash redirect: a write under `.next-auto/` routed through the shell reaches the classifier), then, alone in its Bash call:

```bash
python3 $AUTO verdict N --head <sha> --round 1 --verdict NeedsFixes --report <report path>
```

`<sha>` is the HEAD the review covered. `--verdict` takes `Approved` or `NeedsFixes`: `Step quality: Approved` and `Step quality: NeedsFixes` pass through as written; a re-review's `All findings addressed, no new Critical` is `Approved` and its `Findings remain open` is `NeedsFixes`. It writes the verdict record the merge gate reads at `.next-auto/attended/verdict-<sha>.json` with the keys `"head"`, `"verdict"`, `"reviewer"`, `"model"`, and `"round"` (the reviewer and its model read from the agent definition), keeps the report at `.next-auto/attended/review-<sha>-<round>.md`, and, with `Record` in Conventions, appends `review.verdict` from the two. The kept report is filtered: a finding stays only when its quoted `> ` span occurs in the named file at `<sha>`, the rest move to `### Dropped findings` at its end with their reasons, and the reviewer's text is kept beside it as `review-<sha>-<round>.orig.md`; the fix round and the Findings append below work from the kept findings, so a Critical that verdict N dropped sends no step through a fix round. Critical findings get one fix round, which re-begins step N at its commit: `python3 $AUTO check begin N` (its base is now the step's commit), the fix with its failing test first, the Test and Lint commands, `python3 $AUTO check N`, `python3 $AUTO set N done --note-file /tmp/note.txt` with the fix's evidence, and `python3 $AUTO commit N`, which appends the fix commit's own `step.done`, so the step carries two; then re-review scoped to the fix, recorded as round 2. A Critical that survives is stop (e). Important and Minor findings go to the plan's Findings section:

```bash
python3 $PLAN append prompt_plan.md findings --note-file /tmp/note.txt
```

With `Record` in Conventions, once the last round is recorded, commit the record alone as `chore(record): <slug>`, one operation:

```bash
python3 $AUTO record-commit
```

It commits nothing when the record has no change. The session runs it again after the done check's `done.verdict` line, and after `gh pr create` it records the pull request with `python3 $AUTO pr-opened <n>`, which reads the PR's `headRefOid` from GitHub, refuses when it is not local HEAD, appends `pr.opened` with it and `--mode attended`, commits the record, and pushes the branch again. The done check over the claim has its own file, `.next-auto/attended/done-<sha>.json`. After the done check, save its report with the Write tool and record it, alone in its Bash call: `python3 $AUTO done-verdict --head <sha> --verdict <APPROVED or REJECTED> --model <opus, sonnet, or haiku> --report <path>`, with the model read from the done-check agent's definition, which lives in another plugin, so the session names it. It writes the file with the keys `"head"`, `"verdict"` (`APPROVED` or `REJECTED`), `"reviewer"` (`done-check`), and `"model"`, keeps the report beside it as `.next-auto/attended/done-<sha>.md`, and with `Record` in Conventions appends `done.verdict`; then run `python3 $AUTO record-commit` to commit it. The close-out's `python3 $AUTO merge <n>` refuses without the reviewer's `Approved` `verdict-<sha>.json` or the done check's `APPROVED` `done-<sha>.json` for any commit from the PR head down past its record-only commits to the first commit that changes anything else, and a `REJECTED` done check anywhere on that chain refuses it whatever else approves. A `REJECTED` done check is superseded only by running `done-verdict` again with `--head` at the same sha, which overwrites its file; a done check at a later record-only commit does not lift the earlier veto; a record-only commit changes only regular `.md` files directly under `docs/records/`. A refusal, a repo the owner does not own, and every merge that bypasses a ruleset are the owner's act by number, never this loop's.

Then stop with the report: the steps done with their evidence notes, the reviewer verdict, and the stop reason.

## `/adw:next auto [N]` unattended

Hold-only. It commits to a branch and opens a PR. It never merges, and the guard hook denies merges and force pushes for as long as the run is live.

**Preflight.** One command, fails closed with one line per reason:

```bash
python3 $AUTO preflight prompt_plan.md
```

It refuses unless: the `origin` owner is one of `ADW_OWNERS` (comma-separated GitHub owners in the user's settings `env`; unset, every preflight refuses), the repo is not named in `ADW_NEVER_AUTO` (comma-separated `owner/repo` slugs that are never an unattended target), and the repo is not a fork; the plan validates; the default branch is known; local default contains `origin/<default>`; the checkout is clean; no run-state file already exists; no open PR labeled `next-auto` is on a branch of this plan's unit, one beginning `next-auto/<issue>-` with the plan's `Issue` lowercased, or any open one when the plan has no `Issue`, where a `gh` failure counts as a refusal, not as no PR; and every `PENDING` or `IN PROGRESS` step carries a `Size:` line, the reason otherwise being `plan: Step N carries no Size: line; auto runs need the estimate`. A plan kept out of the repo by `.git/info/exclude` is excluded before the tree is judged, so it never reads as dirt. On success it creates the label, ensures `.claude/`, `.next-auto/`, and any `.env` are ignored, and prints `PREFLIGHT OK`. Any refusal ends the run before anything is created.

**Start.**

```bash
python3 $AUTO start prompt_plan.md
```

This creates the run id, the run directory under `.next-auto/<run-id>/` (outside `.claude/`, whose paths Claude Code treats as sensitive files and refuses to write in non-interactive mode), `state.json` (the marker the guard hook reads), and a worktree at `.next-auto/<run-id>/wt` on `next-auto/<issue>-<slug>-<run-id>`, the `<issue>-` there only when the plan carries `Issue`, branched from local default with `--no-track`. It syncs the environment when a pyproject is present. The worktree's `prompt_plan.md` is the only copy that changes during the run. A plan that is untracked at the root is copied into the worktree at the same path and recorded as such in `state.json`; the shared exclude keeps it out of every stage, and the gate refuses it by name if it is forced in.

With `Record` in Conventions, start first asks the delivery record whether the plan's hash is approved, before it reaches GitHub: without a `plan.approved` line for that hash it prints `START FAILED` naming the missing approval and the hash, and creates nothing.

With a `Shares` line in Conventions, `start` refuses the same way before it reaches GitHub, as `check begin N` does at item 4: `START FAILED` names the other work tree and the class, and creates nothing.

It prints `RUN STARTED <run-id>` and a `/goal` line. **Enter that goal line.** It is what re-prompts the loop after each turn ends; without it the run does one invocation and stops.

**Per step**, up to N per invocation:

1. `python3 $AUTO step-begin K` records base HEAD, marks the step IN PROGRESS, writes `brief-K.md` (Conventions plus the one step), `context-K.md` (the Decisions and Findings sections as they stand plus a roster of steps 1 to K-1 with their states and notes), and `plan-snapshot-K.md` (the plan exactly as the implementer receives it), and captures baseline test counts. With `Record` in Conventions it also snapshots `docs/records/<slug>.md` as `record-snapshot-K.md`, protected by a hash in `state.json` as the plan's is. A `step-begin K` on the step this run just committed is its fix round (item 7): the base is that commit, and the step's first base and snapshots are kept as its origin. The two files stay separate on purpose: the gate authorizes gate-config edits by matching file names against the brief, so a Finding that names `conftest.py` must never reach it.
2. Dispatch the `adw:next-implementer` agent. Give it only: the brief path (say "read this first, it is your requirements"), the context path (say "read this second: what the run has decided and found so far, and the steps before yours"), the worktree path, the spec path, the holdout path, and any interfaces from earlier steps the brief cannot know. The rules live in the agent definition; do not restate them in the dispatch. It replies with the full report as its message body (the harness blocks subagents from writing report files) followed by a status block: `DONE`, `DONE_WITH_RULINGS`, `DECISION_NEEDED`, or `BLOCKED`. Save the report body verbatim to `<run-dir>/report-K.md` before the gate; the reviewer reads it from there.
3. `python3 $AUTO gate K`. This is deterministic and yours, not the agent's: HEAD unchanged, the plan byte-identical to its step-begin snapshot (the implementer never edits `prompt_plan.md`; your own `set` and `append` run after the gate and land in the next step's snapshot), with `Record` in Conventions the delivery record byte-identical to its step-begin snapshot (only the engine's append after commit writes it), with `Holdout` in Conventions the Holdout's hash against the one step-begin recorded, refused before anything is staged, staged files free of secrets and toolchain files and anything over 1 MB, no gate-config file the brief did not name, the per-step size cap, prove-red (the step's tests re-applied to base must fail there), Test, collected and skip and xfail counts against the baseline, then Lint. The size cap is the plan's `Step-size: <n>` in Conventions, 300 without it. Its refusal names the measured count beside the step's `Size: <n>` estimate, or `(no estimate)` for a step without the line. Exit 0 is a pass, and it writes `<run-dir>/result-K.json`, the step's evidence for the delivery record: base head, passed and collected counts, prove-red, lint, and the implementer's `<plugin>:<name>` and model read from its definition. Any other outcome removes that file, and a pass that cannot read the implementer definition, or a prove-red whose base failed only on modules that do not resolve, one of them not the step's, when every check after it passes, is `GATE APPARATUS` (exit 2).
4. **Green:** `python3 $AUTO set K done --note-file ...`, then `python3 $AUTO commit K`: commit reads the note for the delivery record's `mutation` value, so the note is on the plan first, and it says `mutation killed` when the report shows the mutation check ran. With `Record` in Conventions, commit refuses without the gate's result file, with one a commit already used, or when the index is not the tree the gate passed; it completes the file with the sha and the mutation value, and appends `step.done` in the worktree; `COMMIT <sha> RECORD FAILED` (exit 2) means the commit landed and its line did not, so stop the run. A commit that fails after `set K done` is reverted like a red gate, which puts the plan back. Append any rulings from the report with `python3 $AUTO append decisions --note-file ...`. `set` and `append` take no plan path: they always edit the worktree copy, the only one a run may change. Never run `next_plan.py set` against the root copy during a run.
5. **Red, BLOCKED, or a report missing its evidence:** `python3 $AUTO revert K` saves the staged work as a patch, resets the worktree, and restores the plan, and with `Record` the record file, from the step's snapshots. Retry once, giving the implementer the gate's failure output and the patch path. A second failure is `python3 $AUTO set K failed --note-file ...` and the run stops.
6. **Eval steps** run the Eval command after green and map the exit code per `Eval-codes`. An apparatus code is `BLOCKED (apparatus: ...)` and stops the run without touching the system under test.
7. `python3 $AUTO review-package K`, then dispatch `adw:next-reviewer` with the brief, the report, and the package path. Record every round, the first review and the re-review: save the reviewer's report verbatim with the Write tool, then `python3 $AUTO verdict K --head <sha> --round <round> --verdict <Approved or NeedsFixes> --report <path>`, where `<sha>` is the commit `commit K` printed and the verdict values map as at the attended boundary. It writes `<run-dir>/verdict-K-<round>.json`, keeps the report at `<run-dir>/review-K-<round>.md`, and with `Record` appends `review.verdict` in the worktree. Critical findings get one fix round, which re-begins the step at its commit: `python3 $AUTO step-begin K` again, the implementer with the findings verbatim, `python3 $AUTO gate K`, `python3 $AUTO set K done --note-file ...`, then `python3 $AUTO commit K`, which appends the fix commit's own `step.done`; then re-review scoped to the fix as round 2. Still Critical, or a red gate in the fix round, means `python3 $AUTO revert K`: with the fix round open it drops the whole step, both commits, back to the step's first base, keeps the diff as a patch, and puts the plan and the record back as the step first began, so no record line names a dropped commit; then `python3 $AUTO set K failed --note-file ...`, and the run stops. Never drop the commit by hand; the guard hook denies `git reset --hard` during a run for exactly this reason. Important, Minor, and out-of-scope findings go to the plan's Findings section via `python3 $AUTO append findings --note-file ...`. **You never fix findings yourself.** Always put `python3` in front of the script variable when you call it; a variable alone in program position is a program the guard cannot name, and it denies those during a run.
8. `DECISION_NEEDED` is `python3 $AUTO append decisions --note-file ...`, `python3 $AUTO set K blocked-decision --note-file ...`, and a stop.

**Stopping.** The run stops when N steps are done, when a step fails, when a step is blocked, or when `python3 $AUTO size` exits 1 (run-level diff over 500 lines; run it after every commit). On any stop, with `Record` in Conventions, first `python3 $AUTO record-commit` to commit the record's pending lines alone as `chore(record): <slug>` (wrap-up commits any it still finds); then:

```bash
python3 $AUTO wrap-up
```

It reads every step's state from the worktree plan, commits the plan file when the plan is tracked, and writes two files to the run directory: `summary.md` (steps with their states and notes, the Decisions and Findings sections, and every step report) and `pr-body.md` (the same without the step reports and with no absolute paths). It asks `gh repo view --json isPrivate`; a private repo gets `summary.md` as the PR body, a public one (or one whose visibility gh cannot confirm) gets `pr-body.md`. The chosen body is scanned for secret-shaped content section by section before anything is pushed; a hit is `WRAP-UP FAILED: secret-shaped content in <section>` and the marker stays. Then it pushes the branch, opens a PR labeled `next-auto` against the origin repo, prints `RUN STOPPED <reason> PR #n`, and deletes `state.json`, which disarms the guard hook. With `Record` in Conventions it commits any pending record lines alone as `chore(record): <slug>` after the plan and before the push, so the PR opens on a head that carries them; then it runs `<appender> sync <slug>` as committed on the default branch and commits a changed record alone as `chore(record): sync <slug>`, and a failed sync stops wrap-up before the push with the marker kept; once the PR exists, and only when the run committed a step (otherwise it prints `RECORD SKIPPED pr.opened: the run committed no step`), it appends `pr.opened` with the head the PR opened on and `--mode auto`, commits the record alone as `chore(record): <slug>`, and pushes again; a failure there prints `RECORD FAILED after PR #n: <why>` after `RUN STOPPED` and exits 2, with the PR open and the run ended, so wrap-up is not run again. If the push or the PR fails it prints `WRAP-UP FAILED <why>`, exits 1, and leaves the marker in place: the run is still live, fix the cause and run wrap-up again. Both bodies end with a blank line and `Spec:`, `Closes:` and `Approved-by:`, one line each: the plan header's `Spec:` value, the done steps' `Closes:` ids in plan order, and the `by` of the record's `plan.approved` line for the plan's hash, each left out when it has no value; with `Record` and no such line wrap-up stops before the push. The stop reason is derived from the plan (the first BLOCKED or FAILED step the run reached, or completed; a later step pre-marked BLOCKED is not the reason); pass `--reason` only to override it. The worktree, briefs, contexts, reports, and patches stay for review.

**Continuity.** Two contracts carry rulings and findings from one night to the next. For a tracked plan, the run's Status notes, Decisions, and Findings ride the branch in the `chore(plan)` commit, and the morning merge of the PR carries them into the next run's plan. For an untracked plan, wrap-up copies the worktree plan back to the root plan once the PR exists, so the root copy is current before the next preflight. Every entry appended during a run carries a `[run <id>]` tag so an agent's unreviewed ruling reads differently from one the owner wrote by hand. The owner prunes the outbox, the Decisions and Findings sections, during the morning read; the next `context-K.md` shows the implementer whatever survived.

Never merge. Never `git push --force`. Never bypass a hook. The guard hook denies all three while the run is live, and branch protection is the wall behind it.
